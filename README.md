# Concurrent Search Bot

Учебный Telegram-бот на `aiogram 3`, который выполняет поиск по одному пользовательскому запросу сразу в трёх источниках:

- Wikipedia;
- GitHub;
- Stack Overflow.

Проект предназначен для изучения асинхронного программирования на Python, конкурентного выполнения сетевых операций, обработки частичных отказов, таймаутов и ограничения количества одновременных запросов.

## Возможности

Бот:

- принимает текстовый поисковый запрос в Telegram;
- проверяет, что запрос не пустой и не превышает установленный размер;
- запускает поиск по трём источникам конкурентно;
- использует одну общую `aiohttp.ClientSession`;
- ограничивает число одновременно выполняющихся провайдеров через `asyncio.Semaphore`;
- устанавливает таймаут для отдельного провайдера;
- устанавливает общий дедлайн пользовательского поиска;
- сохраняет результаты источников, которые успели ответить;
- отдельно отображает пустую выдачу и ошибки источников;
- разбивает длинный ответ на несколько сообщений Telegram.

## Архитектура

Общий путь пользовательского запроса:
```text
Telegram
    ↓
handler
    ↓
SearchService
    ↓
Wikipedia / GitHub / Stack Overflow
    ↓
ProviderOutcome
    ↓
formatter
    ↓
ответ пользователю
```

### Handler

Handler отвечает только за Telegram-уровень:

- получает объект `Message`;
- проверяет входной текст;
- ограничивает длину запроса;
- передаёт запрос в `SearchService`;
- передаёт результаты форматтеру;
- отправляет одно или несколько сообщений пользователю.

Handler не знает деталей HTTP API внешних сервисов.

### SearchService

`SearchService` координирует поисковые операции:

- хранит зарегистрированных провайдеров;
- запускает их конкурентно;
- ограничивает число одновременно выполняющихся провайдеров;
- обрабатывает таймауты и сетевые ошибки;
- отменяет незавершённые операции;
- возвращает отдельный `ProviderOutcome` для каждого источника.

### Провайдеры

Каждый провайдер работает со своим внешним API и преобразует ответ API в общую модель `SearchResult`.

Провайдеры не зависят от Telegram и не форматируют итоговое сообщение.

### Модели

`SearchResult` описывает один найденный результат.

`ProviderOutcome` описывает итог работы одного источника:

- имя источника;
- список найденных результатов;
- сообщение об ошибке, если источник не ответил.

Пустой список результатов и ошибка являются разными состояниями:
```text
results=[] и error=None
→ источник ответил успешно, но ничего не нашёл

results=[] и error="..."
→ источник завершился с ошибкой
```

Нужен Python версии 3.12 или выше в пределах версии, указанной в `pyproject.toml`.

```

```

## Настройка

Создайте файл `.env` в корне проекта:
```dotenv
BOT_TOKEN=токен_вашего_бота
```

Файл `.env` содержит секретные данные и не должен попадать в Git.

Настройки приложения загружаются в `config.py`. Там же находятся адреса внешних API и основные параметры приложения:

- HTTP-таймаут;
- таймаут отдельного провайдера;
- общий таймаут поиска;
- максимальное число одновременно работающих провайдеров;
- максимальная длина пользовательского запроса.

## Конкурентное выполнение

Провайдеры запускаются конкурентно. Поэтому общее время поиска обычно определяется не суммой времён всех источников, а самым медленным источником, если не возникает очередь на семафоре или таймаут.

Для каждого провайдера создаётся отдельная асинхронная задача.

Явные задачи используются намеренно. Сервису нужно:

- дождаться провайдеров только до общего дедлайна;
- узнать, какие операции завершились;
- сохранить уже готовые результаты;
- отменить незавершённые операции;
- дождаться завершения отменённых задач;
- вернуть частичный результат с понятной информацией об источниках.

Для этой логики используется `asyncio.wait()`. В Python 3.11 и выше `asyncio.wait()` требует задачи или futures, поэтому передача обычных корутин напрямую здесь невозможна.

## Ограничение конкурентности

В `SearchService` используется общий `asyncio.Semaphore`.

Он ограничивает количество одновременно выполняющихся провайдеров во всём процессе бота.

Например:
```text
max_concurrent_providers = 3
```

означает, что одновременно внутри ограниченного участка может находиться не более трёх операций провайдеров. Остальные операции ждут освобождения семафора.

Семафор не ограничивает количество входящих сообщений Telegram. Он ограничивает количество одновременно работающих внешних поисковых операций.

## Таймауты

В проекте используются несколько разных ограничений времени.

### HTTP-таймаут

Настраивается через `aiohttp.ClientTimeout`.

Он ограничивает сетевую операцию через `aiohttp`.

### Таймаут провайдера

`provider_timeout` ограничивает работу одного провайдера после получения разрешения семафора.

Время ожидания свободного места в семафоре в этот таймаут не входит.

### Общий таймаут поиска

`search_timeout` ограничивает весь вызов поиска пользователя:

- ожидание места в семафоре;
- выполнение провайдеров;
- получение результатов;
- ожидание завершения конкурентных операций.

Если общий дедлайн истёк, успевшие источники сохраняются, а незавершённые источники получают понятное сообщение о превышении времени поиска.

## Обработка ошибок

Технические ошибки записываются через стандартный модуль Python `logging`.

Пользователю не показываются внутренние HTTP-коды, traceback или технические сведения о библиотеке. Вместо этого бот отправляет понятное сообщение, например:
```text
Не удалось получить результаты из этого источника. Попробуй повторить запрос позже.
```

При этом в журнале сохраняется техническая информация, необходимая для диагностики.

Ошибка одного источника не отменяет успешные результаты других источников.

## Ограничение длины сообщений Telegram

Telegram имеет ограничение на длину текстового сообщения.

Поэтому результаты сначала разбиваются на отдельные логические блоки, а затем объединяются в сообщения безопасного размера. Готовая HTML-строка не обрезается произвольным срезом, чтобы не повредить HTML-разметку.

Длинные поля отдельных результатов также ограничиваются перед HTML-экранированием.

## Ограничения проекта

Текущая версия проекта имеет следующие ограничения:

- результаты Wikipedia не переводятся;
- GitHub работает без авторизационного токена;
- запросы к Stack Overflow используют публичный API;
- специальная обработка поля `backoff` Stack Exchange API не реализована;
- проект не предназначен для высокой промышленной нагрузки;
- Queue и workers не добавлялись, так как относятся к дополнительному этапу задания;
- постоянный сервер для работы бота не настроен.

## Структура проекта
```text
src/search_bot/
├── __init__.py
├── bootstrap.py
├── config.py
├── formatting.py
├── github.py
├── models.py
├── search_service.py
├── stackoverflow.py
├── wikipedia.py
├── handlers/
│   ├── __init__.py
│   └── search.py
└── probes/
    └── ...
```

`bootstrap.py` содержит функции сборки приложения.

`config.py` отвечает за настройки и переменные окружения.

`handlers/` содержит Telegram-обработчики.

`formatting.py` отвечает за преобразование результатов в сообщения Telegram.

`search_service.py` координирует конкурентный поиск.

Файлы провайдеров работают с конкретными внешними API.

## Проверка проекта

Проверка синтаксиса:
```bash
python -m compileall src/search_bot
```

Запуск бота:
```bash
python -m search_bot.main
```

В каталоге с пробниками находятся отдельные сценарии для проверки:

- работы провайдеров;
- конкурентного выполнения;
- таймаутов;
- ограничения конкурентности;
- отмены незавершённых задач.

Нагрузочные проверки используют подставные провайдеры и не должны выполняться через настоящие внешние API.
